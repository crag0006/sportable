# Access Assistant lab test report, 10 Oct 2026

Local test of the Epic 6 assistant workflow before any production code is written. Everything here ran outside the repository (`idea_Venkat/assistant-lab/`) against the real local API, a local chat model, a local embedding model and a pgvector store on the lab network.

## 1. Setup

| Part | What was used | Production equivalent |
|---|---|---|
| Structured data | Local SportAble API at `127.0.0.1:8000/api/v1` (dev HEAD 9aeebff, local PostGIS: 2,153 venues, 317 programs, Greater Melbourne gazetteer only) | Same API code on Lambda over RDS |
| Chat model | Qwen3.8-Flash-Next 177B MoE (IQ4_XS) on llama.cpp on a lab server, OpenAI-compatible, `reasoning_effort=medium`, temperature 0.2, 35 tok/s | Claude Haiku 5.5 on Bedrock |
| Embedding model | bge-m3 FP16 on llama.cpp on a second lab server, 1024 dimensions, normalised, 8192 context | Titan Text Embeddings v2, 1024 dimensions |
| Vector store | PostgreSQL 17.11 + pgvector 0.8.7 on a third lab server, table `program_chunk` (migration 010 columns without foreign keys), HNSW cosine index | `program_description_chunk` in RDS |
| Tool loop | `lab/chat.py`: one system message, tools in OpenAI format, at most 3 tool rounds, then a forced text answer | `services/assistant/` loop over Bedrock Messages API |

Eight tools: `resolve_location`, `find_venue` (lab only, trigram SQL over `venue_card`), `list_sports`, `search_venues`, `get_venue`, `search_events`, `get_event`, `search_program_descriptions`. Seven are thin wrappers over the existing endpoints and return compact JSON with every facility's `display`, `message`, `source.name` and `publisher_last_updated` copied from the API unchanged.

## 2. What went into the vector store

Only the publishers' own program descriptions (`program.description`, DS-09 AAA Play). 317 programs, all with text, average 549 characters, longest 1,723. The repository chunker (`data/derive/chunker.py`, 500 character target, 80 overlap, sentence breaks) produced 476 chunks (196 programs in one chunk, 93 in two, 28 in three or more). Indexing took 34 seconds with a per-text cache (427 embeddings computed). Rows are tagged `embedding_model_id = bge-m3-fp16` so they can never mix with Titan rows.

Nothing a user types is stored. No facility status, venue record or model output is stored.

## 3. Two retrieval designs compared

- **tool**: the model decides when to call `search_program_descriptions` and writes the query itself.
- **always** (passive): the user's own words are embedded before the model runs, every turn; passages above the floor are injected into the system message; the tool is withdrawn.

## 4. Test set

25 questions in five groups, each with mechanical checks: every `/venues/{id}` and `/events/{id}` link and every "N m" distance in the answer must appear in a tool result; required phrases; forbidden phrases that would only come from the model's own knowledge; expected tools.

| Group | Cases | What it tests |
|---|---|---|
| A discovery | 5 | place resolution, venue search with a facility filter and band, event search, typo handling |
| B venue | 4 | venue by name, page context (`venue_id`) instead of search, unknown facilities said as "no published information", unrecorded opening hours |
| C retrieval | 6 | questions only the description text answers (audible tennis balls, Braille and Auslan signs, transport provided, Melbourne Victory unified football, a published start time) |
| D knowledge leak | 6 | Sydney Cricket Ground, rules of wheelchair basketball, a phone number, pool prices, tram routes, Reclink's website |
| E scope | 4 | physiotherapist, prompt injection, an LGA name, an unknown venue id |

## 5. Results

| | tool mode | always mode |
|---|---|---|
| Passed | 25 / 25 | 25 / 25 |
| Median latency | 12.1 s | 12.2 s |
| Mean latency | 14.0 s | 11.9 s |
| Slowest | 26.1 s | 27.3 s |
| Mean tool rounds | 1.32 | 0.88 |
| Median answer length | 90 words | 79 words |
| Knowledge leaks (group D) | 0 | 0 |
| Ungrounded links or distances | 0 | 0 |

How the 25/25 was reached: the first full run scored 17 and 19 because the checker kept a trailing full stop on links and four case expectations were wrong about the data (the Blind Tennis description does state 6:30 pm; the MCG is a DS-01 venue; a nearby change facility's hours are in the data; "no venue" versus "not"). Those were corrected and the six affected cases re-run after the fixes in section 6. No model answer was edited.

Group D in detail: the model refused the rules question without a tool call, said no phone number or price is published, gave no tram route, used only the attribution text for AAA Play's site, and for the SCG either said it is outside the Victoria register (tool mode, after a `find_venue` that returned Victorian cricket grounds) or returned the capability sentence (always mode). The rule that did the work is rule 0 of the prompt: "whatever you know from training is out of date or wrong for this site; if a tool did not return it, you do not know it".

## 6. Findings that changed the design

1. **The GGUF model sends the string "null" for empty slots.** Three of the first six runs lost a round to a 422. Normalised in the tool runner; Haiku on Bedrock with `strict: true` schemas will not do this, but the normaliser costs nothing.
2. **One system message only.** The Qwen chat template rejects a second system message, so page context (`venue_id`, place, band) is folded into the single system prompt. Keep that shape for Bedrock as well: one system block, cached.
3. **Round cap must force a text answer.** With the cap hit and tools still requested, the first version returned an empty answer. Now the last call is made with `tool_choice=none`.
4. **A facility band is not a venue radius.** Asked for "accessible parking within 250 m", tool mode once answered "no netball venue is within 250 m of the centre of Reservoir". The band semantics are now spelled out in the tool description and the answer is correct in both modes.
5. **Dense similarity alone misses phrases.** "audible tennis balls" scored 0.53 to 0.56 against the Blind Tennis chunk, below the 0.58 floor, while the same program scored 0.72 for "tennis for people who are blind". Fixed with hybrid retrieval: pgvector cosine plus Postgres full-text (`to_tsquery` over OR'd content words), fused by reciprocal rank. A lexical hit below the floor is kept only when the chunk carries at least two of the question's content words and sits within 0.05 of the floor, or three or more words at any score. After that: 5 of 5 relevant questions found their program; 4 of 7 off-topic questions returned nothing; the rest returned genuinely related program text (wheelchair basketball programs for a rules question) which the model ignored or refused correctly.
6. **The floor is model-specific.** bge-m3 puts unrelated questions at 0.50 to 0.56 and relevant ones at 0.61 to 0.72 on this corpus. `ASSISTANT_CONFIG.relevance_floor = 0.35` was written for Titan and must be re-measured there with the same probe set; the contract should say the floor is configured per `embedding_model_id`, not quote a number.
7. **The model writes worse queries than the user.** In tool mode the model turned "Which programs mention audible tennis balls?" into "audible tennis balls" (first run, miss) and later into a 17-word question (hit). The tool description now asks for a full sentence close to the user's words. Always mode avoids the problem by embedding the user's words, at the cost of an embedding call and up to four passages of context on every turn, including venue questions where they are noise.

## 6a. Retrieval ablation: dense, dense + ts_rank, dense + BM25

Run after the main test, with no chat model involved (`lab/ablate.py`): 18 questions each answered by one known program (audible tennis balls, Braille and Auslan signs, Reclink transport, Melbourne Victory, quiet hour at the gym, para table tennis, boccia, 2026 term dates, boxing for Parkinson's, football after stroke, free wheelchair tennis trial, powerchair sport, Sailability, goalball, para-equestrian, Starfish Nippers, chair pilates) and 8 off-topic questions that should return nothing.

BM25 is hand-rolled in SQL (`lab/bm25.py`): three tables derived from `to_tsvector` (term frequency per chunk, chunk length, document frequency), k1 = 1.2, b = 0.75, so it runs on RDS where no BM25 extension can be installed. Rebuilding the tables for 476 chunks takes under a second. The fusion is reciprocal rank (constant 60) over the dense top 12 and the lexical top 12.

| Method | hit@1 | hit@4 | MRR | Recall with the acceptance rule | Off-topic passages returned (8 questions) | Median lexical leg |
|---|---|---|---|---|---|---|
| dense only (HNSW cosine, floor 0.58) | 15/18 | 18/18 | 0.917 | 16/18 | 4 (1 question) | 8 ms |
| dense + ts_rank_cd (OR'd content words) | 16/18 | 18/18 | 0.944 | 18/18 | 9 (3 questions) | 64 ms |
| dense + BM25 | 17/18 | 18/18 | 0.972 | 18/18 | 6 (2 questions) | 18 ms |

What the numbers say:

- Every method puts the right program in the top four. The difference is at rank 1 and in what the acceptance rule lets through.
- Dense alone drops two relevant answers at the floor ("2026 term dates", "boxing for Parkinson's" score 0.50 to 0.55 because the distinctive words are a small part of the chunk). Lowering the floor to recover them would admit the off-topic questions, which sit at 0.50 to 0.56.
- `ts_rank_cd` has no IDF and no length normalisation, so "accessible", "program" and "people" weigh as much as "audible". It fixes recall but doubles the noise.
- BM25's IDF does the filtering by itself. The acceptance rule for a BM25 hit below the dense floor is its score as a share of the query's maximum attainable score: relevant hits scored 0.45 to 0.63, off-topic ones 0.10 to 0.29, so the floor is 0.40 (0.30 when the dense similarity is within 0.05 of its floor). The two residual off-topic cases are a venue question that dense alone also admits (program descriptions that talk about accessible parking and toilets, similarity 0.68) and "renew my car registration" (two chunks that contain "registration" and "Victoria"). Both are the kind of passage the model ignored in the main test.
- Cost: one extra SQL statement per retrieval, about 10 ms more than dense alone at this size.

Decision: the lab now runs dense + BM25 (`RETRIEVAL_LEXICAL=bm25`); the six retrieval cases of section 4 passed 6/6 end to end on it. The chunk index pipeline in production (`data/derive/chunk_index.py`) needs the three BM25 tables rebuilt after each load; one function.

A cross-encoder reranker (bge-reranker-v2-m3 on llama.cpp, or Cohere Rerank if Bedrock Sydney offers it) was not tested: with four passages going to the model there is little left to reorder. It becomes worth measuring if the corpus grows past a few thousand chunks or the rules corpus (DS-11) is added.

## 7. Tool versus passive: recommendation

Both reached 25/25. The difference is where the risk sits:

- Tool mode: risk is a missed call or a weak model-written query. Mitigated by the tool description and by the hybrid lexical leg. One extra model round when used (about 5 to 10 s locally, under 2 s expected on Haiku).
- Passive mode: risk is noise in context on every turn and one embedding call per message. On this run the model never cited an injected passage on a venue or scope question, and refused the rules question even with four wheelchair-basketball passages in front of it.

Recommendation for production: **tool mode, with the hybrid retrieval and the full-sentence query rule**, because it keeps one code path (every fact comes through a tool result the answer builder can check), costs nothing on the 70 percent of questions that are about venues, and leaves the model's choice visible in the logs as a count. Keep the passive injection as a configuration switch (`RETRIEVAL_MODE`) for A/B on staging; it is twenty lines.

## 8. Inputs to contract v0.3

- `POST /api/v1/assistant` request: `question`, optional `context {page, venue_id, event_id, location, distance_m}`, optional `history` (last turns, text only). Response as in ASSISTANT_TOOL_PROTOCOL section A, with `results` and `sources` rebuilt from tool results.
- New read capability needed: venue by name (`GET /venues?q=` or an assistant repository method). Without it "is there parking at Olympic Leisure Centre" cannot be answered; the lab used trigram SQL.
- `/locations/resolve` should accept LGA names (`kind: "lga"`); "Darebin" and "Geelong" are what people say.
- Retrieval passages are the publisher's words: the answer must attribute them (AAA Play attribution line) and never promote a time or place in them to a structured field or a facility status. Both modes did this correctly for the Blind Tennis start time.
- Relevance floor configured per embedding model; hybrid retrieval needs the three BM25 tables (`chunk_term`, `chunk_stats`, `term_df`) beside the chunk table, rebuilt by the derive stage after each load (section 6a).

## 9. Limits of this test

- Local data is Greater Melbourne only (574 suburbs, 317 programs); staging and production hold all of Victoria (529 programs). Geelong and Mildura questions therefore cannot be answered locally.
- One chat model, one run per case, temperature 0.2. Numbers are indicative, not statistics.
- The checker verifies grounding of links and distances mechanically; wording quality was judged by reading all 50 answers.
- Latency is dominated by the local 177B model at 35 tok/s and is not representative of Haiku.
